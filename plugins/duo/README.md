# duo

Fable plans and reviews, Sonnet works. An orchestrated delivery flow for Claude subscriptions, where the usage limit is the budget. `/duo:duo <task>` (or `/duo <task>`, see below): Fable writes the plan first, Sonnet workers implement at the effort the task needs, and Fable reviews the result.

## Install

```
/plugin marketplace add googlarz/duo
/plugin install duo@duo
```

Run it as `/duo:duo <task>`; a bare `/duo` is unconfirmed. The agents are namespaced (`duo:duo-high`); the skill finds them either way.

## Stages

| Stage | Agent | Model / effort |
| --- | --- | --- |
| Explore | Explore subagent | Haiku / Sonnet low |
| Plan (once) | `duo-advisor` writes it, the orchestrator checks it | Fable high, no Edit/Write |
| Implement | `duo-low` ... `duo-max` | Sonnet, effort low to max by difficulty |
| Purely mechanical edits | `duo-haiku` | Haiku low, always verified |
| Verify | `duo-verifier` | Sonnet medium, fresh agent, no Edit/Write |
| Review (on the combined diff) | `duo-reviewer` | Fable high, no Edit/Write |
| Stuck after Sonnet max | `duo-opus` | Opus xhigh |
| Last resort or very high stakes | `duo-fable` | Fable high |

## Rules of thumb

- **Gate budget:** advisor (writes the plan) at most once, reviewer once as the final pass, plus one early pass only for risky tasks, `duo-opus` only with your consent.
- **Fast path:** <= 2 tasks, none marked risky, skips advisor and reviewer (the orchestrator writes the plan); only the verifier runs. **Lite path:** 3-4 low-risk tasks, the advisor still writes the plan, keep the verifier and one final review. On Haiku the plan gate is mandatory and wins over the fast path and the 80% skip (except at >= 95%). Default effort ceiling is `high`; xhigh/max only after a failed attempt or an unclear root cause.
- **Escalation cap:** max 2 attempts per task; a failure jumps straight to the Sonnet tier the defect list implies.
- **Usage limits:** fresh `~/.claude/duo-usage.json` at >= 80% skips the plan gate and early reviewer, caps workers at medium and stops escalation at medium (it reports instead); the final reviewer then runs only for tasks the plan marked risky, otherwise the orchestrator reviews itself; at >= 95% nothing new starts. A limit marker (`~/.claude/duo-limit-hit.json`) written by the `StopFailure` hook is a hint: it counts only if newer than the flow start and the five-hour window has not reset. If the orchestrator's own turn died, say "continue" and the flow resumes from the report. Details in [docs/usage-limits.md](docs/usage-limits.md).
- **Small tasks:** use `opusplan` or plain Sonnet instead.
- Worker agents are generated by `scripts/gen-agents.sh` (edit the shared body there, not the generated worker files).
- Effort levels low, medium, high, xhigh and max for Sonnet 5.5 are per Claude Code docs (`model-config`); on older Sonnet an unsupported level falls back to the highest supported one. Check your version.

## Set up usage awareness

Run `/duo:setup` once: after you say yes it adds a small helper to your status line (your own status line keeps working) and duo keeps the helper up to date by itself. Manual steps are in [docs/usage-limits.md](docs/usage-limits.md). Without `duo-progress` and without this helper the guard is off (no usage reading, no downshifting) and duo says so in the plan. The cache can also go stale (>15 min) during long subagent waits; the skill then ignores it.

## Read-only agents

`duo-advisor`, `duo-reviewer` and `duo-verifier` declare `disallowedTools: Edit, Write` (a documented subagent frontmatter field, not among those ignored for plugin subagents) and a `tools` allowlist. They keep `Bash`, which can still write files; their instructions tell them not to.

## With duo-progress

With the [duo-progress](../duo-progress) mod installed, the orchestrator reports the plan and accepted tasks to a progress bar, and workers report their steps to the agents panel (tiers `duo-low` ... `duo-verifier`). Without the mod those calls are skipped.

Install instructions are in the [repository README](../../README.md).
